# PRD-40 — Playback Reliability, Observability & Routing Baseline

**Status:** Approved — frozen for implementation
**Supersedes:** nothing. Extends PRD-37 (universal media compatibility & adaptive playback engine) and PRD-39 (native extension & playback standards).
**Scope:** `cs3_windows` — Electron main process (`electron/`), renderer (`src/`)
**Repo:** `D:/projects/cs3/cs3_windows`

---

## 1. Context

PRD-37 and PRD-39 established the inspection → decision → multi-engine routing pipeline. That architecture is correct and is **not** being replaced. Three rounds of architecture review confirmed the pipeline shape and produced a large set of proposed refinements to routing, capability modelling, and engine preference.

Those refinements are not the subject of this PRD.

Review established that the routing debate (remux-vs-mpv ordering, transcode demotion, libmpv migration) **cannot be settled without playback data that does not currently exist**. Meanwhile, three defects were identified that cause reproducible playback failure on real content today, independent of routing.

This PRD therefore covers exactly two things:

1. **Fix the reliability defects.**
2. **Build the measurement substrate** that makes every deferred decision empirically answerable.

Routing behaviour is deliberately left unchanged. The current `DecisionEngine` policy becomes the **control group** for all Tier 2 work.

### Non-goals

The following were reviewed, agreed as directionally correct, and explicitly deferred. They are documented in §9 so the reasoning is not lost, but they are **out of scope for this PRD** and must not be implemented as part of it:

- Any change to the strategy ladder ordering or engine preference
- `capabilities()` / `selectEngine()` split
- Launch-time capability matrix (`decodingInfo`, `isTypeSupported`, container table)
- DRM capability object and `unplayable` terminal state
- Subtitle capability model and DOM bitmap-overlay renderer
- Audio mode setting and audio-driven routing
- Parallel fan-out inspection pipeline
- `renderTarget` capability model
- libmpv migration
- Disk-backed transformed assets

## 2. Objectives

| # | Objective | Success condition |
|---|---|---|
| O-1 | Long playback survives signed-URL expiry | A 2-hour playback of a source with a 10–30 min token completes without HTTP 403 interruption |
| O-2 | Inspection stops silently failing on non-head-metadata containers | Probe failure rate is measured and classified by container; MP4/MOV `moov`-at-end and MPEG-TS cases resolve without hitting `blindFallbackPlan` |
| O-3 | Every playback session is observable | 100% of `PlaybackSession` lifecycles emit a telemetry record, including failures and aborts |
| O-4 | Seek cost on piped transforms is a known number, not an assumption | A measured p50 for restart-on-seek on a `-c copy` remux is reported |
| O-5 | Application orchestration overhead is bounded and enforced | `INV-PERF-1a` holds in reporting |
| O-6 | Wall-clock startup is tracked as product health | `INV-PERF-1b` reported, not gated |

## 3. Invariants

PRD-37 defined `INV-RACE-1` … `INV-RACE-4`. Those remain in force unchanged. This PRD adds:

### INV-PERF-1a — Orchestration overhead (hard engineering gate)

```
probeParseMs
+ capabilityLookupMs
+ decisionMs
+ engineAttachMs
-------------------------
p50 <= 150 ms
p95 <= 300 ms
```

Excludes all network transfer. This is the portion of startup latency the application controls.

**Enforcement rule:** no new work may be added to the pre-playback path unless it is cached, parallelised, or cheap enough to hold this budget. If a proposed capability step cannot hold it, the step is wrong — not the budget.

### INV-PERF-1b — Wall-clock to first frame (product health metric)

```
timeToFirstFrameMs
-------------------------
p50 <= 1200 ms
p95 <= 2500 ms
```

**Tracked and reported. Not a gate.** A 2 MB range probe over a 5 Mbps link alone consumes ~3 s; gating on wall-clock would put the application in permanent violation for reasons outside its control and would degrade the invariant into something nobody enforces.

### INV-LEASE-1 — Refresh and reconnect are distinct recovery paths

Connection-level failure and lease-level expiry are different conditions with different remedies. They must not share a code path, a retry counter, or a budget.

### INV-TELEM-1 — No routing change without a policy version bump

Any change to `DecisionEngine` behaviour requires a manual increment of `decisionPolicyVersion`. Telemetry emitted under different policy versions must never be pooled when comparing routing outcomes.

## 4. Tier 1 Work Items

### 4.1 `SourceLease` — signed-URL lifecycle management

**Problem.** Provider links carry cryptographic expiry, typically 10–30 minutes. `MediaProxy` currently auto-reconnects on upstream termination, but reconnecting to an *expired* URL only produces a faster 403. On a two-hour film with a 15-minute token this is a certainty, not an edge case. It affects mpv and FFmpeg more severely than `<video>`, because those hold a single long-lived connection and have no mechanism to renegotiate.

**Design.**

```ts
// electron/media/sourceLease.ts

interface SourceLease {
  /** Stable logical identity. Survives every re-resolution. */
  sourceId: string

  /** Re-derives a fresh signed URL from the provider. */
  resolve(): Promise<ResolvedSource>

  /** Known or inferred token deadline, if the provider exposes one. */
  expiresAt?: number

  /** Whether re-resolution is possible at all for this source. */
  refreshable: boolean

  /** Remaining refresh attempts. Decrements on each attempt, not each success. */
  refreshBudget: number

  retryPolicy: {
    maxRefreshes: number        // suggested default: 4
    minIntervalMs: number       // suggested default: 30_000 — floor between refreshes
    backoff: 'fixed' | 'exponential'
  }
}

interface ResolvedSource {
  url: string
  headers: Record<string, string>
  cookies?: string
  expiresAt?: number
}
```

**State machine.** Refresh and reconnect are separate transitions out of `connected`:

```
                    ┌─────────────┐
                    │  connected  │
                    └──────┬──────┘
                           │
      ┌────────────────────┼────────────────────┐
      │                    │                    │
 connection            lease                refresh
 failure               expired              budget
 (socket reset,        (expiresAt           exhausted
  TCP timeout,          passed, or
  upstream EOF)         signed-token
      │                  failure pattern)       │
      ▼                    │                    ▼
┌───────────┐              ▼             ┌──────────────┐
│ reconnect │      ┌────────────────┐    │   terminal   │
│  (same    │      │ refresh source │    │   failure    │
│   URL)    │      │ (new signed    │    └──────────────┘
└─────┬─────┘      │  URL, same     │
      │            │  sourceId)     │
      │            └───────┬────────┘
      │                    │
      └────────┬───────────┘
               ▼
         ┌───────────┐
         │ connected │
         └───────────┘
```

**Refresh trigger conditions.** Refresh fires only on:

- `expiresAt` known and passed (or within a safety margin — suggest 60 s), **or**
- a signed-token failure *pattern*: HTTP 403/401 on a source that previously streamed successfully, where the failure is not attributable to a header/cookie/geo condition

**Refresh must not fire** on the first request of a session, on 404, on 5xx, or on any 403 where the source has never successfully streamed — those indicate a resolution or header problem, not expiry. Blind refresh-on-403 risks a `403 → resolve → 403 → resolve` loop and hammers the provider.

**Budget enforcement.** `refreshBudget` decrements on every attempt regardless of outcome. `minIntervalMs` is a hard floor between attempts. Exhaustion is terminal for the session and must surface a clear user-facing message, not a silent stall.

**Integration.** `MediaProxy.register(token, lease)` replaces registration of a raw URL. The proxy holds the lease, not the URL. Every engine — `<video>`, hls.js, Shaka, FFmpeg, mpv — continues to see a stable `http://127.0.0.1:<port>/stream/<token>` endpoint and is unaware that re-resolution occurred beneath it. This is the existing `MediaProxy` value proposition (single network abstraction across all engines) extended to cover token lifetime.

**Why `sourceId` matters now.** Without stable logical identity, telemetry treats every re-resolved URL as a distinct media source, and failure patterns like the following become unanalysable:

```
403 after 14 min  ─┐
403 after 42 min   ├─ same sourceId → one analysable pattern
refresh succeeded  │
refresh failed    ─┘
provider changed URL shape
```

### 4.2 Container-aware inspection strategies

**Problem.** `MediaInspector` performs a single `Range: bytes=0-2097152` head probe. This silently under-reports on:

- **MP4/MOV with `moov` at the end** (non-faststart) — head bytes contain no stream table
- **MPEG-TS** — default `probesize` / `analyzeduration` are too small to enumerate all streams, particularly secondary audio and subtitle tracks
- **HLS / DASH** — a manifest describes the media; probing the manifest's *bytes* is a category error

Under-reporting flows into `blindFallbackPlan`, which by `INV-RACE-3` must re-encode — so a metadata miss silently converts a free remux into a full transcode.

**Design.** Replace the single strategy with typed dispatch. A tail probe is **not** the universal fallback; it is the MP4/MOV-specific remedy.

```
                        Source URL
                            │
                            ▼
                 ┌──────────────────────┐
                 │  URL / type detect   │   (free, synchronous)
                 └──────────┬───────────┘
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
    .m3u8 / .mpd      known container       unknown
        │                   │                   │
        ▼                   ▼                   ▼
  ┌───────────┐      ┌─────────────┐    ┌──────────────┐
  │ Manifest  │      │ head probe  │    │  progressive │
  │  parser   │      │ (0–2 MB)    │    │    probe     │
  │ (HLS/DASH)│      └──────┬──────┘    └──────────────┘
  └───────────┘             │
                     complete? ──yes──> Capability Model
                            │
                            no
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
     MP4 / MOV         MPEG-TS           other / unknown
          │                 │                 │
          ▼                 ▼                 ▼
  ┌──────────────┐  ┌────────────────┐  ┌──────────────┐
  │  tail probe  │  │ raise          │  │ progressive  │
  │ Range:       │  │ -probesize     │  │ probe        │
  │ bytes=-2MB   │  │ -analyzeduration│ │              │
  └──────────────┘  └────────────────┘  └──────────────┘
```

**Strategy table.**

| Detected type | Primary | On incomplete |
|---|---|---|
| `.m3u8` | HLS manifest parser | — (manifest is authoritative) |
| `.mpd` | DASH manifest parser | — (manifest is authoritative) |
| MP4 / MOV / M4V | head probe `bytes=0-2097152` | tail probe `bytes=-2097152` |
| MPEG-TS / M2TS | head probe | re-probe with raised `-probesize` / `-analyzeduration` |
| MKV / WebM | head probe | progressive probe (widen head window) |
| Unknown / no extension | head probe | progressive probe |

**Definition of "incomplete".** A probe is incomplete when the returned metadata lacks any of: container `formatName`, video `codec`, video `bitDepth`, or contains zero audio streams on a source whose container permits audio. Incompleteness must be recorded distinctly from probe *error* in telemetry (§4.3).

**Ordering constraint.** Manifest parse for HLS/DASH replaces ffprobe for that source; it is not additive. Only one inspection strategy produces the authoritative `MediaMetadata` per source.

### 4.3 Per-session telemetry

**Problem.** The remux-vs-mpv ordering question, the transcode-demotion question, and the libmpv-justification question are all currently unfalsifiable. They have consumed three rounds of architecture review and remain undecided because no data exists.

**Design.** `PlaybackSession` emits exactly one record per session lifecycle, on terminal state — including error, user abort, and engine-switch termination. Records are written locally; no requirement for remote collection in this PRD.

```ts
// electron/media/playbackTelemetry.ts

interface PlaybackTelemetryRecord {
  // ── Identity & provenance ────────────────────────────────
  sessionId: string
  sourceId: string                  // stable across re-resolution (§4.1)
  sourceFingerprint: string         // hash of container + codecs + resolution + audio layout
  timestamp: number

  appVersion: string
  electronVersion: string
  decisionPolicyVersion: number     // manually bumped on any routing change — INV-TELEM-1
  capabilityFingerprint: string     // hash of (Electron, Chromium, OS build, GPU, driver)

  // ── What was chosen ─────────────────────────────────────
  selectedEngine: 'html5' | 'hlsjs' | 'shaka' | 'mpv'
  selectedStrategy: Strategy        // existing ladder enum, unchanged
  renderSurface: 'dom' | 'native-window'
  subtitleMode: 'none' | 'webvtt' | 'ass-native' | 'bitmap-native' | 'unavailable'

  // ── Inspection ──────────────────────────────────────────
  inspectionStrategy: 'manifest-hls' | 'manifest-dash' | 'head' | 'head+tail'
                    | 'head+probesize' | 'progressive'
  container: string
  probeIncomplete: boolean          // metadata gaps — distinct from probeError
  probeError: string | null
  probeBytesTransferred: number
  probeNetworkMs: number            // network transfer only

  // ── Latency breakdown ───────────────────────────────────
  // INV-PERF-1a components:
  probeParseMs: number
  capabilityLookupMs: number
  decisionMs: number
  engineAttachMs: number
  // INV-PERF-1b:
  timeToFirstFrameMs: number

  // ── Runtime outcome ─────────────────────────────────────
  playbackSeconds: number
  seekCount: number
  seekRestartCount: number          // piped-transform restarts (§4.4)
  seekRestartMsSamples: number[]    // per-restart cost
  stallCount: number
  stallTotalMs: number

  // ── Lease behaviour ─────────────────────────────────────
  leaseRefreshAttempts: number
  leaseRefreshSuccesses: number
  reconnectCount: number            // distinct from refresh — INV-LEASE-1

  // ── Termination ─────────────────────────────────────────
  terminalState: 'completed' | 'user-abort' | 'fatal-error'
                | 'lease-exhausted' | 'engine-switch'
  fatalError: string | null
  transitionCount: number           // engine switches mid-session
}
```

**`decisionPolicyVersion` is load-bearing.** It is immutable for a given build and manually incremented whenever routing behaviour changes. Without it, Tier 2 routing changes blend into the baseline and the before/after comparison this entire PRD exists to enable silently stops working.

**`capabilityFingerprint` composition.** Minimum: Electron version, Chromium version, Windows build, GPU vendor/device, driver version. Note that Windows HEVC Video Extensions can be installed or removed from the Store without *any* of those changing — so the fingerprint must incorporate a live probe result, not just a version tuple. A cached `decodingInfo` answer for a known HEVC profile, re-verified at launch, is sufficient.

**Metric reporting conventions.** Sample-size-aware reporting is mandatory. p95 on a small n is noise, and architecture decisions must not be made from a tiny tail:

| n | Report |
|---|---|
| n < 30 | raw values and max only |
| 30 ≤ n < 100 | p50 + raw max |
| 100 ≤ n < 300 | p50 + p95, flagged as provisional |
| n ≥ 300 | p50 + p95 as operational metrics |

These are reporting conventions, not statistical laws. The binding rule is the last column: no routing or architecture decision from a small-n p95.

### 4.4 Restart-on-seek for piped transforms

**Problem.** Seekability is a property of *delivery*, not of the transform. An fMP4 remux over a pipe is exactly as unseekable as a full transcode over a pipe — in both cases the FFmpeg process must be restarted at an offset. Current behaviour on seek within a piped transform is unmeasured.

**Design.** Implement seek-as-restart correctly, then measure it.

```
seek(targetSec)
   │
   ├─ kill current FFmpeg process
   ├─ respawn:  ffmpeg -ss <targetSec> -i <proxyUrl> -c copy ... -f mp4 pipe:
   │            └─ -ss BEFORE -i  → input seeking (index-based, fast)
   ├─ reattach pipe to <video> / consumer
   └─ record elapsed → seekRestartMsSamples[]
```

`-ss` **before** `-i` is required. Input seeking uses the container index and is fast; output seeking decodes and discards from zero and is not.

**Expected cost** for `-c copy` remux: ~300–800 ms. This is the number O-4 requires. **Do not build disk-backed transformed assets.** That converts a low-cost remux into a local storage subsystem — cache lifecycle, quota, cleanup, concurrency, range coordination, seek-before-produced-data — and the measured restart cost is very likely acceptable without any of it. Revisit only if the measured p50 proves otherwise.

**Reporting.** Report measured p50 per strategy. `REMUX_CONTAINER` and any transcode strategy must be reported separately; their restart costs differ by an order of magnitude and pooling them destroys the signal.

### 4.5 Performance instrumentation

Implement the two invariants as reported metrics with clean separation between application overhead and network transfer.

```
timeToFirstFrameMs  ────────────────────────────────────────────►

├─ probeNetworkMs ─┤├─ probeParseMs ─┤├ capabilityLookupMs ┤
                    ├─ decisionMs ─┤├─ engineAttachMs ─┤
                    └──────────── INV-PERF-1a ─────────────┘
└─────────────────────── INV-PERF-1b ───────────────────────┘
```

`probeNetworkMs` and `probeBytesTransferred` must be captured at the `MediaProxy` layer so that `INV-PERF-1a` can be computed by subtraction without ambiguity. A slow CDN must never be attributable to application overhead.

## 6. Definition of Done

Tier 1 is complete when **all** of the following hold:

- [ ] `SourceLease` implemented with `sourceId` stable across every re-resolution
- [ ] `expiresAt`, `refreshBudget`, and `retryPolicy` enforced; budget exhaustion produces a clear user-facing terminal message
- [ ] Reconnect path and refresh path are structurally distinct — separate transitions, separate counters, separate budgets (`INV-LEASE-1`)
- [ ] A 2-hour playback of a source with a 15-minute token completes with zero 403 interruptions
- [ ] Container-typed inspection dispatch implemented per §4.2 strategy table
- [ ] Probe failure rate classified by container and reported; `probeIncomplete` distinguished from `probeError`
- [ ] Every playback session produces exactly one telemetry record, including error, abort, and engine-switch terminations
- [ ] `appVersion`, `electronVersion`, `decisionPolicyVersion`, `capabilityFingerprint` present on every record
- [ ] Restart-on-seek implemented with `-ss` before `-i`; measured p50 for `-c copy` remux **stated as a number**
- [ ] `INV-PERF-1a` computed and reported with network transfer excluded
- [ ] `INV-PERF-1b` reported as product health
- [ ] Sample-size-aware reporting conventions applied to all percentile output

**No routing change ships as part of Tier 1.** Current routing is the control group.

**On the libmpv gate specifically:** session frequency is the wrong metric. ## 9. Settled positions carried forward

Conclusions reached during review that are **not** implemented here but must not be re-litigated. Recorded so the next architecture round starts from the settled state.

### Engine philosophy

```
Web playback is the DEFAULT surface — because of DOM compositing,
not because of decode capability.

MPV is the native compatibility ESCAPE HATCH.

FFmpeg is TRANSFORMATION INFRASTRUCTURE, not a primary playback engine.

libmpv is deferred until render-target/compositing is designed and proven.
```

### Compositing is the real engine constraint

The binding question is not *can the engine decode this* but **can the engine decode this while preserving the application's rendering model**. Any stream routed to mpv is a stream where `VideoPlayer.tsx` becomes a remote control for a surface it cannot draw on — React overlays, track menus, PiP, rounded corners and animations do not composite over a native window. This is the actual reason web playback is preferred, and the actual reason libmpv matters eventually: getting mpv output into a controllable texture, not "tighter integration."

Future capability model (Tier 2+):

```ts
renderTarget = {
  surface: 'dom' | 'native-window' | 'texture',
  overlays: boolean,
  alpha: boolean,
  hdr: boolean,
  fullscreen: boolean,
  pip: boolean
}
```

### Cheap remux keeps its place

`REMUX_CONTAINER` for MKV + H.264 + AAC runs at ~30× realtime and keeps playback in the DOM. "FFmpeg is a transformation service, not a player" must not be read as an argument against remux. Remux stays above `MPV_NATIVE` pending §8 data.

### Seekability is a delivery property

Not a transform property. A piped remux and a piped transcode are equally unseekable; the remedy is correct restart-on-seek, not classifying transforms as "seek-preserving."

### `decodingInfo` does not solve containers

`MediaCapabilities.decodingInfo()` reports **decoder** support and must be queried for both `type: 'file'` and `type: 'media-source'` — Chromium can answer differently for the MSE path than the plain `<video src>` path. It cannot answer Chromium's **demuxer** restriction: Matroska is gated to WebM codecs, so an MKV carrying H.264 will return `supported: true, smooth: true` and still refuse to load. Container support remains a separate hard-coded table.

`canPlayType()` is dropped as a decision input — it returns `"probably"` where `decodingInfo` returns `{supported, smooth, powerEfficient}` for the same query. `MediaSource.isTypeSupported()` is retained because it answers a different question. Three signals:

```
isTypeSupported()   →  can this MSE pipeline accept this type?
decodingInfo()      →  can this environment decode this configuration well?
container table     →  can this engine actually demux this container?
```

### Codec support is build- and platform-dependent

PRD-37's absolute statements ("Chromium does not ship Dolby decoders", "Chromium cannot decode HEVC") are not universally true across Electron/OS/GPU-driver combinations. **Action for PRD-37:** replace with —

> Chromium/Electron codec support is platform- and build-dependent. HEVC, AC-3/E-AC-3, DTS, TrueHD and other formats cannot be treated as universally available across Electron deployments. Capability must be probed per installation, not assumed.

### DRM-unavailable is terminal for the build

`tryAnotherEngine` for DRM is dead code. Stock Electron or CastLabs Electron is a **build-time constant** — the runtime cannot be hot-swapped mid-session. mpv cannot decrypt Widevine/PlayReady at all, so falling through to mpv on encrypted content ships a garbled-output bug instead of a clear message. The correct model is `unplayable` with a reason code that drives the UI string.

### Bitmap subtitles: DOM overlay, not OCR

OCR is unsuitable for a live playback path — thousands of images, per-frame latency, poor accuracy on stylised subtitles. The viable third option is decoding PGS/VOBSUB to timed PNGs via FFmpeg and compositing them in the DOM using PGS's own position and timing data. Fallback enum:

```ts
bitmapFallback: 'native' | 'dom-overlay' | 'disable'
```

`'ocr'` is removed.

### Audio: ship the setting, not the detector

Three-way user setting — **Stereo / Surround / Passthrough**, default Stereo. Do not build a Windows audio-topology detector without evidence of need. `AudioContext.destination.maxChannelCount` is read once at launch **for discoverability only** (`> 2` → surface the audio mode picker during onboarding); it is never a routing input.

Intended behaviour when implemented:

```
Stereo       → browser-friendly audio; AAC conversion where necessary
Surround     → preserve multichannel; MPV where the browser path would downmix
Passthrough  → prefer native path
```

### Objective function

Every future change to CloudStream 3's playback path is judged against:

```
MAXIMIZE
  playback success · UI compositing · seek quality · audio fidelity
  subtitle fidelity · hardware acceleration · DRM compatibility

MINIMIZE
  startup latency · CPU · GPU · disk · memory
  engine switching · implementation complexity

DO NOT OPTIMIZE FOR
  fewest playback engines
```

### Deliberately not over-engineered yet

libmpv · disk-backed transformed media · OCR subtitles · automatic DRM recovery · complex automatic audio routing · parallel fan-out inspection while `INV-PERF-1a` holds

### First implementation artifact

`electron/media/sourceLease.ts`
